# Verify recipient-specific access

Use for a person/team transfer or changed/unverified access context. For each required source distinguish accessible, unavailable/denied and unverified, with evidence and scope. Producer readability, a tracked path or team label cannot establish recipient access. Denied, truncated, unperformed and complete-empty reads are different states.

1. Inspect actual recipient-context evidence where available. Record whether the basis is a supplied role matrix, earlier probe, current role read or no probe. A simulated role view does not establish OS/service ACLs.
2. Keep usable authorized locators and exact gaps. Never copy denied/private payloads to another channel, widen permissions or publish a source to manufacture access. An accessible substitute is useful only when identity/applicability are established.
3. Check the handoff payload against that recipient scope, retaining supported next work and the specific owner/access decision for each blocked dependency. Avoid further access ceremony where current sufficient evidence already establishes it.
4. Distinguish prepared handoff, source access verified and fresh-reader resumption. The reader receives only permitted current sources and the handoff, then locates objective/corrections, relevant checks, remaining work and next action. Author context or an intended evaluator answer is not reader evidence. State which recipient/context was actually observed.
