# Coordinate a standing program

Use when [Workflow's routing decision](../SKILL.md#choose-the-scope-of-coordination) establishes sustained work beyond one agent's session budget. An explicitly requested controller for a bounded task uses [delegation](delegation.md) without requiring the program machinery here. Reuse that procedure for assignments, capabilities, briefs, independent contexts, acceptance and resource accounting; the applicable domain skills own specialist planning, review and verification.

## Frame and retain the program

Establish an observable completion predicate, scope, delivery tracks, genuine dependencies, review/integration gates, authority and resource budget. If one agent with useful ordinary workers could finish within the available session budget, use ordinary or tailored bounded work instead. Resolve consequential open decomposition through the applicable domain planning procedure; use `luminekit-arena` for consequential unresolved alternatives.

Assign the program owner controller-only coordination through the execution-assignment procedure in [delegation](delegation.md), respecting the task and selected profile. A current eligible controller needs no additional coordinator. Add a track coordinator only when observed coordination load exceeds what one controller can manage, with a bounded track, resources and rollup responsibility. Each added layer must justify its context and coordination cost.

Use existing tracker, plan and workspace owners for recoverable state; use `luminekit-tasks` for actual task-system operations. Retain the controlling constraints, unit owners/dependencies/status, current output/revision pointers, review and verification evidence, active worker identities, pending effects, decisions and cumulative resources. Link existing records rather than duplicating them into a mandatory store or schema. Keep an actual unfinished-state gap through `luminekit-continue`; a transcript or worker summary alone is not the program's completion evidence.

## Prove a unit before expanding

Take one representative unit through necessary planning/review, implementation, verification and authorized integration before increasing concurrency substantially. This checks the brief, unit boundary, acceptance and handoff while failure is contained. For cheap repeated units, the first normal unit can serve this purpose; specialist novelty or risk may justify separate review or verification. Reuse sufficient current evidence rather than repeating a pilot for an unchanged unit shape.

Release ready work as reviewed prerequisites become available. Parallelize across independent ownership boundaries and cap concurrent work at what the controller can inspect and the resource budget can sustain. Give dependent workers the actual accepted upstream contracts, outputs and review dispositions; ordering alone does not transfer that context. Prefer fewer coherent assignments over fragmented workers or a full panel at every stage.

## Accept, integrate and replan

Handle completions through the actual host's lifecycle rules. Reconcile each result to its unit and actual output, classify completed/partial/failed/pending work and inspect the evidence before dependent dispatch. Refill useful capacity as work becomes ready; scheduled polling or a separate queue runtime is not assumed.

Plan integration alongside unit delivery. In controller-only mode, assign integration edits and executable checks to workers. Tie review and verification verdicts to the actual combined source/artifact revision and relevant configuration; changed inputs reopen affected evidence. Passing worker checks does not establish combined acceptance. A dedicated verifier is useful for independent judgment or consequential behavior, not merely to repeat a trivial command; required independent gates still apply.

Bound retries and optional expansion within remaining resources and user authority. When a shared assumption, acceptance condition or capability fails, hold affected dependent dispatch and repair or replan that cause. Preserve unaffected valid work and unique partial results. Reconcile late outputs against current decisions before use. A replacement follows actual cancellation and launch authority; missing work is neither silently absorbed by a controller nor counted complete.

## Recover and close

At session boundaries, use `luminekit-continue` to reconstruct current artifacts, unfinished units, active workers, pending effects, assignments and resources before resuming. Reconcile actual host state before replacements or repeated effects; recovery does not change the controller's role or reset the budget.

At closeout, account for every dispatched unit and worker, inspect the integrated result against the original completion predicate and report actual coverage, blocked gates, remaining work and resources. Leave review, security, publishing or merge gates pending when their evidence or authority is absent. Program ownership grants no additional commit, push, merge or deployment authority.
