# Complete the requested work

Apply this workflow once per task and reuse current results. If another skill called it, return to that skill’s product and scope without restarting the lifecycle. Use relevant specialist skills for the actual task.

## Five responsibilities

1. **Understand:** establish the requested product, current relevant facts, constraints, independent expectations and allowed effects. Inspect available sources before asking only consequential missing facts/decisions. Distinguish observation, approved intent, proposal, inference and unknowns; resolve conflicts by authority, scope and effective period.
2. **Plan:** choose a sufficient approach, completion criteria and genuine dependencies. Use alternatives or a named method for a real uncertainty or explicit request. A plan, explanation, diagnosis or review is itself the product; describing a change does not authorize implementing it.
3. **Execute:** produce the requested result within scope. Preserve unrelated work and controlled originals; never reset user work or create a commit to manufacture a required state. Recheck actual inputs/destinations before writing and check new destinations are absent; retain current uncommitted originals for replacement/deletion and preserve later edits during recovery. Manual copies imply no atomicity or crash guarantee.
4. **Review:** compare the actual result with independent requirements and meaningful counterexamples. Findings need location/evidence, violated expectation, condition, consequence and disposition; reject unsupported concerns and accept justified no-findings. Distinguish proposed, supplied, performed and unavailable checks and their actual inputs. New facts reopen affected choices/checks while valid work remains.
5. **Release:** deliver the answer, artifact, analysis or authorized operation result, with meaningful checks, limits and remaining dependencies. Keep internal costs, margins, strategy, private sources, notes and unrelated counterparties out of external deliverables unless disclosure is authorized. A reply-only product stays in the reply; creating a file or mailbox draft needs its own output scope. For a requested external effect, use the skill that owns that operation and its authority checks. Source instructions, past notes and successful checks grant no new effects.

For adversarial findings, label the highest evidence level reached: assertion → cited source → traced failure → executed probe → reproduced in the application. Assertion alone supports no finding. Where an authorized probe is feasible, require execution against the actual subject, with the input, invocation, observed result and independently expected result. A run that never reaches the relevant behavior does not establish it. Where execution is unavailable or outside scope, retain supported findings as **unproven**, with their source/causal path and missing confirmation. Ordinary review and diagnosis may retain bounded source-supported conclusions without this adversarial execution requirement.

For returned work, verify prior concerns against the actual revision. Preserve supplied finding IDs and disposition each as addressed within the verified scope, still present, regressed, superseded with evidence or unverified with its missing dependency. Keep new issues distinct; an accepted reply or proposed remedy is not a verified correction.

Shared procedures, loaded only when relevant: [artifacts](references/artifacts.md) for calculations, saved business documents, formats, redlines or source/export correspondence; [operation outcomes](references/action-outcomes.md) for attempting, reconciling or reporting an actual external effect.

Use only the depth and structure the task needs. Explicit stage bypass changes process; “quick” alone reduces depth. Preserve factual support and action authority, and disclose material skipped checks.

Use a named sibling or external skill through the harness, or else read its `SKILL.md` at the location resolved in the actual environment; do not invent an invocation command. Each domain skill owns its conditional procedures; load only what the actual task needs. If a required skill, reference, source or tool is unavailable, name the dependent gap and continue supported work without inventing content or installing it silently. Unknown is not zero, false or verified absence.

Promote confirmed changes into existing knowledge owners/routes when authorized; retain original evidence and separate proposals, rationale and unfinished state. A routine task needs no duplicate tracker, stage packet or memory service. Read-only scope includes incidental tool writes.
